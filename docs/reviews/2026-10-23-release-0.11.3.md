## 4. 认证修复结论

### 已确认的客户端问题与处理

1. 启动探测过去将学习服务错误、网关壳和超时合并为“未登录”，随后可能调用已保存密码。现在区分已验证、明确失登和服务不可用。只有可靠账号快照允许显示该账号的本地视图；该视图不会把底层会话提升为已验证。
2. 正常 HTTP 401、明确登录表单或明确失登响应保留恢复路径。网关壳、限流、服务故障、缺失 CSRF 和未知 JSON 结构保留原始失败，不据此自动重新提交密码。手动登录、2FA 和已有服务会话建立流程继续使用现有机制。
3. 安装指纹采用共享读取与生成过程，并通过本地与原生镜像恢复；同一已知账号可复用 Cookie。换账号、未知归属及退出执行清理隔离。
4. 恢复时先核对两份持久化账号快照，再水合和访问学校。账号归属冲突或存储读取失败采取保守处理；记住的凭据仅能注入同账号会话。退出清理失败会保留错误，并移除当前账号视图。
5. 原生 Cookie 仓在完整清理时推进账号代次并立即保存空仓。reqwest Cookie provider 在锁内验证请求代次，旧请求无法写回当前 Cookie；前端正文、clone 和派生种票继续校验代次。
6. 云盘 WebView、静默 profile 和 Token 提交流程绑定操作起点。Token setter 同步核对凭据版本，涵盖“已经退出，但旧取票请求此时才开始提交”的窗口。GitLab 种子写入与最终删除串行执行，清理完成后再次清空 TS Cookie 镜像。
7. 主认证、直接 CAS、选课恢复路径停止自动添加 `singleLogin/deviceName`，同时过滤隐藏字段带回的同名参数。既有指纹和信任票继续使用；验证码阶段由用户明确选择的保存信任设备流程保留。

### 故障原因与证据边界

用户报告曾同时出现 `AUTH-FAIL reason=unexpected-page stage=credential-entry` 和 `webvpn-guide len=2760`，随后又恢复登录。这两项诊断来自认证入口和学习探测各自的响应，现有材料不足以证明二者为同一份 HTML。

本轮进行一次使用全新 CookieJar 和应用 User-Agent 的匿名公开 GET，经过 WebVPN、OAuth 后获得正常统一认证表单：HTTP 200，17,524 字符，含公钥字段。此请求没有提交账号或密码，只证明检查时入口正常。故障时原始响应尚未取得；学校网关短时异常与现象一致，仍属于推断。

公开表单的 `singleLogin` 表示“本次登录使用信任浏览器访问校内其他系统时不必再输入账号密码（统一登录）”，默认未勾选。已确认客户端过去自动携带该选项；**尚未以真实账号验证学校是否每次新增持久信任因子、何时去重及具体去重条件**。因此本次可确认减少自动授权请求与身份抖动，不能宣称已经证明并完全消除学校端所有重复信任记录。
